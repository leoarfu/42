Above the PHY:
RRC, PDCP, RLC & the RRM Scheduler

1. Where This Sits in the Stack

M5-5 built the physical and MAC layers of the NTN air interface — the resource grid, MODCOD-equivalent link adaptation, HARQ. M7-6 picks up at the transport layer — TCP/QUIC riding across the ISL mesh. Between them sits the part of the RAN protocol stack that owns per-connection state, ciphering, and reliable delivery to a specific UE. That's the gap this page fills.

Two of the three layers here are control/user-plane protocols that terminate at a specific network function — in Release-17 transparent NTN, that function is the ground-based gNB, not the satellite (M5-5 §2). Everything in §2–4 below therefore runs on the ground today, and only migrates to the satellite if the architecture goes regenerative — the same fork M5-5 §6 and M7-1 already flagged for the payload and the mesh respectively.

2. RRC — Connection & Mobility Management

Radio Resource Control (TS 38.331) owns the UE's relationship with the network above the bit level: which cell it's attached to, what its security context is, and what triggers a handover. Three states:

  • RRC_IDLE — no dedicated resources; the UE monitors paging and re-selects cells on its own.
  • RRC_INACTIVE — a Release-15 addition: context is kept at both ends so reconnection is fast, without holding a dedicated radio bearer meanwhile. The efficient middle state for bursty traffic.
  • RRC_CONNECTED — dedicated resources, network-controlled mobility. This is the state everything in M5-5 and M6-5's handover choreography assumes.

RRC carries the signalling that makes a handover a handover rather than a dropped call: measurement reports, handover commands, and — the NTN-specific addition — the broadcast satellite ephemeris and common timing-advance/Doppler parameters that M5-5 §3 described. Those aren't a separate NTN sub-protocol; they're carried as RRC system information, the same channel that carries cell configuration on any terrestrial gNB.

THE HANDOVER CHOREOGRAPHY, ONE LAYER DOWN M6-5 §7 described handover as make-before-break: authorise on the new path while the old still carries. RRC is the protocol executing that — the measurement report, the handover command naming the target cell, and the security-context transfer all ride RRC signalling, timed against the K_offset-adjusted grant arithmetic of M5-5 §3. The "network-side switching" latency M6-5 quotes in the low tens of milliseconds is substantially RRC signalling delay.

3. PDCP — Header Compression, Ciphering, Handover Continuity

Packet Data Convergence Protocol (TS 38.323) sits directly above RLC and does three jobs: robust header compression (ROHC) to shrink IP/UDP/RTP overhead on the air interface, ciphering and integrity protection, and — the piece that matters most for a system with frequent handovers — in-order delivery and duplicate detection across a handover using a PDCP sequence number that survives the RLC/MAC reset underneath it.

The handover-continuity function is why PDCP exists as a separate layer rather than folding into RLC. When a UE moves to a new cell, RLC and MAC state resets — new HARQ processes, new ARQ state — but PDCP's SN and reordering window carry across the transition, so packets in flight during the handover arrive in order at the receiver instead of being lost or duplicated. For a terrestrial macrocell handing over every few minutes this is a minor robustness feature. For a LEO earth-moving-cell architecture handing every terminal over every few tens of seconds (M5-5 §6), it's a continuously-exercised mechanism, not an edge case.

4. RLC — The Reliability Layer HARQ Hands Off To

Radio Link Control (TS 38.322) has three modes:

  • Transparent Mode (TM) — no header, no segmentation; used only for specific broadcast/control channels.
  • Unacknowledged Mode (UM) — segmentation and reassembly, no retransmission. Used where a higher layer or the application tolerates loss (VoIP-class traffic).
  • Acknowledged Mode (AM) — segmentation, reassembly, and ARQ: the receiver reports missing segments, the transmitter retransmits. This is the mode M5-5 §4 pointed to without naming it, when it said GEO NTN disables HARQ feedback and "reliability moves to the RLC layer."

That's the mechanical answer to the thread M5-5 left open: with HARQ feedback off, the MAC layer stops retransmitting at the slot level, and RLC AM's ARQ — running end-to-end over the full satellite RTT rather than per-slot — becomes the sole automatic-retransmission mechanism. It's slower per retransmission (bound by the full RTT, not a HARQ round) but it's the layer designed to tolerate exactly that, since RLC ARQ was never assumed to be fast — HARQ was always the fast layer and RLC the backstop. GEO NTN simply promotes the backstop to primary.

5. RRM Scheduling Algorithms

M5-3 established what the scheduler divides (multiple access schemes) and what it's discharging (the harmonic-sum efficiency loss of contention and framing). It never specified how the scheduler decides who gets which resource block when — that's the algorithm layer, and it's genuinely a different discipline from the physical-layer material the rest of M5 covers.

Three canonical scheduling metrics, all computing a priority score per user per scheduling interval and awarding the resource to the highest score:

  • Round robin — cycles through users regardless of channel quality. Fair in allocation count, wasteful of capacity: a user in a deep fade gets the same slot as one in clear sky.
  • Max C/I (max carrier-to-interference) — always serves whoever has the best instantaneous channel. Maximises total cell throughput, starves users with structurally worse geometry (edge-of-beam, low elevation) — the opposite failure mode from round robin.
  • Proportional fair (PF) — the industry-standard compromise. Priority score = instantaneous achievable rate ÷ that user's own recent average throughput. A user scores high either because their channel is good right now or because they've been under-served recently — both trigger an allocation, which is what keeps a temporarily-shadowed or low-elevation user from starving while still exploiting good channel moments opportunistically.

Beam-level RRM extends the same logic across the two-dimensional problem M3-5 already introduced conceptually (beam-hopping, demand-matching): a full RRM engine allocates power, frequency sub-channels, and dwell time jointly across beams, using the same per-user metrics as an inner loop and an interference-aware outer loop that accounts for co-channel beams (M4-6's C/I territory) before finalising an allocation.

ILLUSTRATION — PROPORTIONAL-FAIR SCORING

Not spine-integrated, not exercised, no knowledge check attached — a minimal illustration of the PF metric only, to make §5 concrete rather than descriptive.

def proportional_fair_pick(users, alpha=0.1):
    """
    users: dict {user_id: {"inst_rate": Mbps this slot, "avg_rate": Mbps, EWMA}}
    alpha: EWMA smoothing for the running average (0 < alpha <= 1)
    Returns the user_id scheduled this slot, and updates avg_rate for all.
    """
    scores = {u: d["inst_rate"] / max(d["avg_rate"], 1e-6)
              for u, d in users.items()}
    winner = max(scores, key=scores.get)

    for u, d in users.items():
        served_rate = d["inst_rate"] if u == winner else 0.0
        d["avg_rate"] = (1 - alpha) * d["avg_rate"] + alpha * served_rate
    return winner, scores

# Three terminals: one at high elevation (good, steady channel),
# one at low elevation (weaker, steadier), one mid-beam fading in and out.
users = {
    "A_high_elev":  {"inst_rate": 120.0, "avg_rate": 100.0},
    "B_low_elev":   {"inst_rate": 40.0,  "avg_rate": 35.0},
    "C_fading":     {"inst_rate": 180.0, "avg_rate": 30.0},  # good instant, starved recently
}
winner, scores = proportional_fair_pick(users)
print(winner, scores)
# C wins this slot despite B's lower instantaneous rate, because C's score
# (180/30=6.0) beats both A (120/100=1.2) and B (40/35=1.14) — PF rewards
# either a strong channel right now or a low recent average. Run this in
# a loop over synthetic elevation/fade traces and B's low but steady rate
# will still accumulate fair long-run share, unlike under max-C/I.
WHAT THIS DOESN'T SHOW Real RRM schedulers add QoS-class weighting (a voice/control packet outranks best-effort regardless of PF score), buffer-status awareness (don't schedule an empty queue), and — for LEO specifically — elevation/Doppler-aware channel prediction rather than a single scalar "inst_rate." This is the metric core, not a product scheduler.

7. Why It Matters for LEO Specifically

None of this is generically "useful to know." Three places it changes LEO system design in ways that don't show up at terrestrial cell sizes:

PDCP's handover-continuity job runs continuously, not occasionally. A terrestrial macrocell exercises PDCP's cross-handover reordering window a few times an hour per user. An earth-moving-cell LEO architecture (M5-5 §6) exercises it every few tens of seconds, for every terminal, all the time. A PDCP implementation whose reordering window and buffer sizing were tuned for terrestrial handover rates will either buffer too little (packet loss at every handover) or too much (added latency) at LEO's handover cadence — this is a real sizing parameter an access-network architect has to revisit, not an inherited default.

RLC AM's promotion to primary reliability layer at GEO is a design choice with a LEO converse. Because LEO's shorter RTT keeps HARQ duty factor high (M5-5 §4 — 31–62% at LEO versus 1–3% at GEO), LEO NTN can leave HARQ as the fast primary layer and keep RLC AM as backstop, the terrestrial-normal division of labour. GEO can't. An architect evaluating a multi-orbit hybrid system (M1-4) needs to know this split changes between the LEO and GEO legs of the same network, not that one config serves both.

The scheduler's per-user metric needs a satellite-aware channel predictor, and this is exactly where the ephemeris-driven pre-compensation of M5-5 §3 pays a second dividend. A terrestrial PF scheduler estimates "instantaneous achievable rate" from a recent CQI report — fine, because the channel a terrestrial UE saw a few milliseconds ago is a good predictor of the channel now. A LEO terminal's channel is moving through a continuously-changing elevation angle and range (M6-4, M6-5); a scheduler that treats the last CQI report as current is scheduling against stale geometry. Because the terminal already computes its own position and has ephemeris (the same data that drives TA/Doppler pre-compensation), the scheduler can — and production LEO systems do — feed elevation/range-predicted SNR into the PF metric instead of relying purely on reported CQI, buying a few slots of lookahead that a terrestrial scheduler doesn't need and doesn't have.

Regenerative payloads move all three layers into orbit. M5-5 §6 flagged Release-19 store-and-forward as "reintroducing the regenerative payload through the back door" for IoT-NTN. The general version: any regenerative architecture terminating the gNB on the satellite (M7-1's mesh territory) also moves RRC, PDCP, and RLC termination on board — which is a payload processing and radiation-tolerant compute requirement, not just a routing one. This is the direct line from "L2/L3 protocol termination point" to Module 3's payload architecture and the digital transparent processor question that sits at the centre of the payload-experience gap this page's parent conversation was actually about.
